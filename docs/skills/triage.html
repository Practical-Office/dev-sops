Triage

Confirm the claim, set Severity and Priority separately, pick a Triage State, and route to human or agent.

Why

Severity ≠ Priority

Severity is impact; Priority is scheduling. Mixing them burns capacity. Triage also decides whether the ticket is ready for work or needs more info.

When

Use this skill

  • A new bug report lands (or returns from needs-info)
  • Reporter suggested Severity/Priority — triage confirms or changes
  • Category might be enhancement, not bug — route correctly

How

What triage sets

  • Category — exactly one: bug or enhancement
  • Severity — severity/s1 … severity/s4
  • Priority — priority/p0 … priority/p3
  • State — needs-triage · needs-info · ready-for-agent · ready-for-human · wontfix

Work starts only at ready-for-agent or ready-for-human. Then route to /diagnosing-bugs.

Inputs / outputs

InputsOutputs
Bug report (template fields); optional grill sessionCategory; Severity; Priority; Triage State; routing decision

Anti-patterns

What to avoid

  • Starting /diagnosing-bugs while still needs-info
  • Collapsing Severity and Priority into one P1–P4 scale
  • Guessing missing template fields instead of grilling or returning

Micro-scenario

Abstract example

A reporter files “login broken” with no steps. Triage moves to needs-info, asks for repro steps via comment. On return, confirms bug, sets severity/s2 and priority/p1, state ready-for-agent, and assigns the card.
